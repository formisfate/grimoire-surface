# Findings — 2026-10-31

What building the surface turned up in the corpus. Nothing here was silently "fixed": the join-table
changes are recorded because they change what the corpus claims about itself, and the one real data
defect is left for the owner rather than decided by an agent.

Everything below was **measured**, not inferred. The numbers in the corpus's own documentation had
drifted; these are the current ones.

---

## 1. The entry count was wrong in three places, in three different ways

| Source | Claimed | Actual |
|---|---|---|
| `grimoire/README.md` | 3,085 | **3,083** |
| `grimoire/AGENTS.md` | 3,085 | **3,083** |
| `grimoire/CLAUDE.md` | 3,073 | **3,083** |
| Measured | — | **3,083** (3,062 excluding 21 system/reference entries) |

The cause is traceable: the chakra pass of 2026-10-31 merged `above_crown` and `alta_major` into
`crown_chakra` — which deleted two entries — and the counts were never re-measured. `CLAUDE.md`,
already demoted to a pointer for exactly this reason, was 10 behind rather than 2.

This is the failure mode the corpus's own `AGENTS.md` warns about: *"the reason to re-measure rather
than trust a number."* The counts are now generated. `scripts/gen-catalog.mjs --check` fails when
`catalog.json` drifts, and the test suite checks the same thing independently.

## 2. The reference count was understated by a third

`grimoire-graph.ts` says "~22,000 references". The real figure is **34,999** resolved references, all
of them resolving (after the §7 pass).
The comment predates the 2026-10 expansion (1,478 → 3,083 entries) and was never revised. Not a
defect in the data — just another stale number — but it is the number a reader uses to judge how
much graph there is, so it is worth correcting.

## 3. The join table had five gaps, and they were all the same shape

229 values in join-typed fields resolved to nothing. 228 of them fell into two classes, and neither
was a data defect — the table was incomplete:

**a. Vocabularies sitting in join-typed fields (28 values).** `not_joins` exists for exactly this.
Five rules were added:

| Field | Why it is not a join |
|---|---|
| `lunar_mansions.talisman` | a prose description of the mansion's talisman *image* ("A black man with his hair bound in black cloth…"), not a reference to `planetary_talismans.json` |
| `ogham.letter` | the Latin letter a few is read as (`B`, `L`, `F`, `S`), not a `hebrew_letters.json` id |
| `moon_phases.aspects` (under `deities`) | deity-aspect vocabulary (`crone_and_dark_goddess`) |
| `moon_phases.phase` (under `menstrual_correspondence`) | a menstrual-cycle phase, not a Wu Xing phase |
| `vayus.direction` | movement quality (`inward and upward`), not a compass bearing |

**b. The tarot suits were never indexed (160 values).** The four suits are `id`s of objects inside
`tarot_system.suits`, not top-level entries. `AGENTS.md` says so explicitly and 160 values name
them. The surface now indexes them as `nested: true` (they have no `/grimoire/e/<id>` page).

After both: **one** unresolvable reference remains.

## 4. The one real defect — left for you

```json
// bagua_areas.json
{ "id": "tai_chi", "name": "Tai Chi", "trigram": "tai chi", "direction": "center", … }
```

`tai chi` is not a trigram. It is the pole the eight trigrams turn around — the entry's own note
says so: *"The centre is the Tai Chi, the pole around which the eight trigrams turn; it is earth and
it belongs to no single direction."*

So the entry is **right**, and the field is the wrong kind for it. The corpus has a convention for
this: `none_traditionally` is a legal meta value meaning "none by tradition", and it fits exactly.

**Not changed**, because changing a value in an entry is editorial work and the alternative is a
one-line decision:

- **Option A (recommended):** set `trigram` to `none_traditionally` on `tai_chi`. The reference then
  resolves as a meta value, the dangling count goes to 0, and nothing else changes.
- **Option B:** declare `tai chi` a conceptual value, the way `the_center` and `the_circle_itself`
  are already legal in `elements.tools` — but that means extending `meta_values`, which changes the
  corpus's rulebook to accommodate one entry.
- **Option C:** leave it. The surface reports `dangling_references: 1`, which is honest, and the
  website already renders the value as plain text.

## 5. A contradiction in the table, resolved locally

`talisman` appears in **both** `global` joins (→ `planetary_talismans.json`) and `vocab_keys` ("keys
that hold vocabularies, never references"). The walker consults `global` and ignores `vocab_keys`, so
the prose talismans in `lunar_mansions` were being treated as references.

Resolved for the one file that has the problem. The general contradiction is still there and is a
decision, not a bug: `direction`, `letter`, `aspect` and `colors` are all in `vocab_keys` *and*
declared joins, and making `vocab_keys` win globally would break the places where they genuinely
are references. `not_joins` is the right instrument; `vocab_keys` may be vestigial.

## 6. Two declarations the walkers ignore

- `joins.json` declares **19** `containers` (keys that only group more values). The walkers in both
  the website and this surface use their own hard-coded set of **13** — the declared set adds
  `associated`, `correspondences`, `dignities`, `invocation_approach`, `related` and `timing`.
- `vocab_keys` (180 entries) is exported and never read by any walker.

Neither causes a wrong answer today — the 13-key set is the one that was tuned — but they are
specifications that do not govern anything, and the next person will assume they do. Either wire
them up and re-measure, or delete them. Not changed here, because switching to the 19-key set would
change which values are walked and that needs a measured before/after rather than a guess.

## 7. The deferred calls, cleared (same day)

§4 and §6 were left open on 2026-10-31 "for the owner". He cleared them the same evening: *"i remember
i said defer the decisions lets make them now so we can clear any remaining confusion."* Every item
below was decided and applied.

**a. The bagua centre has no trigram — `none_traditionally` (§4, Option A).**
`bagua_areas.tai_chi.trigram` was `"tai chi"`, which is the pole, not one of the eight. It now reads
`none_traditionally` — a legal meta value and the corpus's own idiom for "there is none" (17 uses
against 2 for bare `none`). The unresolved-reference count is now **zero**.

**b. `hexagrams.element` → `hexagrams.phase` (new).**
All 64 hexagrams carried the five Wu Xing ids under the *Western* field name — exactly what the table
forbids. Renamed, the values are real joins (64 new edges) and the `not_joins` rule that was hiding
the problem is retired. `chinese_zodiac.element_cycle` stays a `not_joins` field: its values are Wu
Xing ids too, but it is the *generating cycle*, not a single phase — and it had been declared against
`elements.json`, the wrong file, so the declaration is gone and the veto stays as a guard.

**c. `vocab_keys` deleted (was §6).**
It could never be correct: it was a *name-level* list in a system where whether a value is a reference
is decided *per file*, and 12 of its 180 names are genuine joins somewhere (`aspect`, `direction`,
`letter`, `suit`, `ruler`, `order`, `correspondences`, `trigram`, `element_cycle`, `talisman`…).
Nothing read it. A field nobody declares is simply not a join, so the list was a second, contradictory
rulebook. Removed from `joins.json` and from the generated TypeScript.

**d. `containers` now governs (was §6).**
Both walkers hard-coded a 13-key subset of the 19 the corpus declares. The two sets were measured
against the corpus and produce **identical** graphs (34,936 references, 1 dangling, both ways), so the
declared set is now used in both places and the hard-coded copies are deleted.

**e. Three dead join declarations removed (new).**
`talisman`, `talismans` and `element_cycle` were declared joins with nothing to join to. `talisman`
appears 28 times, all prose image-descriptions in `lunar_mansions.json`; `talismans` appears nowhere;
`element_cycle` pointed at `elements.json` while holding Wu Xing ids. All three removed from `global`,
and the two `not_joins` rules that existed only to veto them were retired with them.

**Net effect:** 180 global joins (from 183), 41 scoped, **13 `not_joins`** (from 15), no `vocab_keys`,
one container set, **34,999 references, 0 unresolved, 0 duplicate ids**.

The lesson worth keeping: every item in §4 and §6 was a case of *the same rule written twice, in two
places, and drifting*. The join table in the corpus plus one walker that reads it is the whole fix;
the follow-on work is to keep refusing a second copy.
